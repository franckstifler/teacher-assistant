# Deploying to production

## Environment variables

The server refuses to start when a required variable is missing.

| Variable | Required | What it is |
|---|---|---|
| `DATABASE_URL` | yes | `ecto://USER:PASS@HOST/DATABASE` |
| `SECRET_KEY_BASE` | yes | `mix phx.gen.secret` |
| `TOKEN_SIGNING_SECRET` | yes | `mix phx.gen.secret` (sign-in tokens) |
| `PHX_HOST` | yes in practice | The public host name, e.g. `app.example.cm`. Links in emails and on receipts use it. |
| `PHX_SERVER` | for releases | `true` to start the web server |
| `PORT` | no | Defaults to 4000 |
| `POOL_SIZE` | no | Database connections, default 10 |
| `BREVO_API_KEY` | yes | Sends invitations, magic links and password resets |
| `MAIL_FROM_ADDRESS` | yes in practice | The sender, verified in Brevo, e.g. `no-reply@scolaka.com` (also the default) |
| `MAIL_FROM_NAME` | no | The sender's name, default « Scolaka » |
| `TELEGRAM_BOT_TOKEN` | no | With `TELEGRAM_CHAT_ID`: operator alerts on Telegram (see « Telegram alerts ») |
| `TELEGRAM_CHAT_ID` | no | The chat the alerts go to |
| `UPLOADS_DIR` | yes (set by the Docker image to `/data/uploads`) | Where logos, signatures, stamps and student photos are stored. The server refuses to start if the directory doesn't exist or isn't writable. |

Changing `SECRET_KEY_BASE` invalidates the QR and check codes already printed on
receipts, return notes, warnings and report cards.

## HTTPS

The production build only works over HTTPS: plain HTTP is redirected to HTTPS
(with HSTS), and the session cookie is marked `Secure`. Put the app behind a proxy
or load balancer that terminates TLS for `PHX_HOST` and forwards requests with the
`X-Forwarded-Proto: https` header (Caddy, nginx, Fly.io and most hosts do this by
default). Requests to `localhost` are not redirected, for health checks.

## Email with Brevo

The app sends email through Brevo's API (free tier: 300 emails a day).

1. Create a Brevo account.
2. **Verify the domain** you send from: Brevo → Senders, Domains & Dedicated IPs →
   Domains → Add a domain. Add the DNS records Brevo shows (Brevo code, DKIM, DMARC) at
   your domain registrar and wait for Brevo to mark them verified. Without this, mail
   lands in spam or is refused.
3. **Add the sender** `MAIL_FROM_ADDRESS` (e.g. `no-reply@<your domain>`) under Senders.
4. **Create an API key**: SMTP & API → API keys → Generate. Set it as `BREVO_API_KEY`.
5. Deploy, then check: invite a staff member to a school and confirm the email arrives
   (also look in the spam folder the first time).

In development, emails are not sent: they appear at `/dev/mailbox`.

## Docker on a Hetzner server

The `Dockerfile` was generated by `mix phx.gen.release --docker`. The image holds the
release only; uploaded files live outside it, on the server's disk, so a new
image never loses them.

**Once**, on the server:

```sh
sudo mkdir -p /srv/teacher_assistant/uploads /srv/teacher_assistant/backup
# The app runs as `nobody` (uid 65534) inside the container
sudo chown 65534:65534 /srv/teacher_assistant/uploads
# Variables from the table above, one NAME=value per line, readable by root only
sudo install -m 600 /dev/null /srv/teacher_assistant/env
```

**Each deploy**, from a checkout of the code on the server:

```sh
docker build -t teacher_assistant .
docker run --rm --env-file /srv/teacher_assistant/env \
  -v /srv/teacher_assistant/uploads:/data/uploads \
  teacher_assistant /app/bin/migrate
docker rm -f teacher_assistant
docker run -d --name teacher_assistant --restart unless-stopped \
  --env-file /srv/teacher_assistant/env \
  -v /srv/teacher_assistant/uploads:/data/uploads \
  -p 127.0.0.1:4000:4000 \
  teacher_assistant
```

The `-v` line is what keeps the uploads. Without it the container stops at
startup with « the uploads volume is not mounted », instead of storing photos
inside the container where the next deploy would delete them. Port 4000 is only
open to the server itself: put Caddy or nginx in front for HTTPS (see above).

The build context leaves out `priv/uploads/` and `priv/repo/*.local.exs`
(`.dockerignore`): dev photos and real schools' seeds never go into an image.

## Errors

Unhandled errors (a page or request that crashed, a background task that failed, any
other process that crashed) are stored in the app's own database and grouped: the same
error is one line, with how many times and when it last happened. Operators see them
in the console, under **Erreurs** (`/admin/errors`), and the overview counts the open
ones under « À traiter ».

Each operator with an e-mail address gets an e-mail (through Brevo) when an error is
new, or comes back after being marked resolved: not at every occurrence. Mute an error
in `/admin/errors` to stop its e-mails while still counting it. A resolved error is
deleted 30 days later.

An error keeps where it happened (page, action, task) and for whom (school, user and
operator ids), never what was typed or sent: no form contents, query strings, IP
addresses or task arguments (`TeacherAssistant.ErrorReporting.Filter`).

Nothing to configure: the tables come with the migrations (`bin/migrate`).

## Telegram alerts

Optional. With `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` both set, the operators'
Telegram chat gets a message when:

- a school signs up and waits to be verified, with its name, town and `/admin` link;
- an error is new or comes back (the same events as the e-mails above, muting included);
- every morning at 07:00 (school time): schools waiting to be verified, schools gone
  quiet or never used, open errors and jobs abandoned since yesterday. It is sent even
  when there is nothing to handle (« Rien à traiter »): no message means the app or
  its alerts are down.

Error messages carry the error's kind, where it happened and its link, never its text:
Telegram is a third party and the text may hold a pupil's data. Read it in
`/admin/errors`.

To set it up:

1. In Telegram, talk to **@BotFather**, send `/newbot` and pick a name. It answers with
   the bot token: that is `TELEGRAM_BOT_TOKEN`.
2. Open the new bot and send it any message (a bot can only write to a chat that wrote
   to it first). For a group, add the bot to the group and post a message there.
3. Find the chat id: open `https://api.telegram.org/bot<TOKEN>/getUpdates` and read
   `"chat":{"id": …}` (a group's id starts with `-`). That is `TELEGRAM_CHAT_ID`.
4. Set both on the server and restart the container.
5. Check: in the console (`/admin`), panel « Système », press « Envoyer un message
   test ». A wrong token or chat id is named in the error shown.

Without them nothing is sent, and nothing is queued.

## Backups

The uploads directory is not a backup: it dies with the disk or the server. Copy
it off the server every night, with the database, and keep them together: the
database only stores file paths, so one without the other restores bulletins
and cards with blank photos, logos and stamps.

A Hetzner Storage Box (or Backblaze B2) with `restic` is enough. In root's crontab,
e.g. `30 2 * * * /srv/teacher_assistant/backup.sh`:

```sh
#!/bin/sh
set -eu
export RESTIC_REPOSITORY="sftp:uXXXXXX@uXXXXXX.your-storagebox.de:/teacher_assistant"
export RESTIC_PASSWORD_FILE=/root/.restic-password
DATABASE_URL="$(sed -n 's/^DATABASE_URL=//p' /srv/teacher_assistant/env | sed 's/^ecto:/postgresql:/')"

# Database first: files are never overwritten or deleted, so every path in the
# dump is already on disk when the files are copied.
pg_dump --format=custom --file=/srv/teacher_assistant/backup/db.dump "$DATABASE_URL"
restic backup /srv/teacher_assistant/uploads /srv/teacher_assistant/backup/db.dump
restic forget --keep-daily 14 --keep-weekly 8 --keep-monthly 12 --prune
```

Run `restic init` once before the first backup, and keep the restic password
somewhere other than the server. Test a restore once, on another machine:
`restic restore latest --target /tmp/restore`, `pg_restore` the dump into an
empty database, start the app with `UPLOADS_DIR` pointing at the restored
uploads, and open a published bulletin.
