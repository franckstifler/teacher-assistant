# P2.10 — School fees, tranches & payment status

**Status:** Approved design
**Date:** 2026-07-08
**Builds on:** P2.1 (school workspaces, roles incl. `bursar`, permissions), P2.2 (students / enrollments / class groups), P2.5 (form-master scoped access), P2.6 (academic year / period plumbing)

## Purpose

Give the school an *intendant* (bursar) the billing core: define each class's fee
schedule as an **échéancier** (ordered tranches with amounts + due dates), record
student **payments**, apply per-student **adjustments** (bourses, APEE waivers), and
compute each student's **balance** and a display-only **payment status** (à jour / en
retard / soldé) against the tranche deadlines. Form masters see their class's status
so they know who is behind ("chasse aux élèves" visibility) — but this increment
performs **no automatic blocking or gating**.

## Scope

In scope:
- Per-class fee schedule = an ordered list of tranches (label, amount in FCFA, due date).
- Manual payment records per student (amount, date, method, reference, note).
- Optional per-student adjustments (a credit reducing what is owed, with a reason).
- Pure balance + status computation against the tranche deadlines and a reference date.
- Bursar/admin management UI; form-master read-only class balances.

Out of scope (deferred / YAGNI):
- **No automatic blocking / fee-based gating of any surface** — the KB flags automated
  exclusion as plausible-but-grey and "configurable/overridable, never automatic"; a
  later increment can add overridable enforcement on top of this ledger.
- No payment-gateway / mobile-money integration — payments are recorded manually.
- No per-tranche payment allocation — payments are a running total against cumulative
  due (see §2).
- No receipt / statement PDF print in v1 (a printable statement is a later increment).
- No school-wide or per-level shared schedules — schedules are per class-group.
- No fee-type-level breakdown (tuition vs APEE vs exam) — the tranche label carries
  that; per-student variance is handled by adjustments.

## 1. Data model

One `Ash.Type.Enum` and three resources (Ash 3 house style: `use Ash.Resource,
otp_app: :teacher_assistant, domain: TeacherAssistant.Academics, data_layer:
AshPostgres.DataLayer, authorizers: [Ash.Policy.Authorizer]`; `policy always() do
authorize_if always() end`; `uuid_v7_primary_key :id`; `timestamps()`; FK `on_delete`
inside `postgres do ... references do ... end end`). **All money amounts are integer
FCFA** — the CFA franc has no minor unit, so no Decimal/cents.

**Enum**
- `TeacherAssistant.Academics.PaymentMethod` —
  `[:cash, :mobile_money, :bank_transfer, :other]`.

**`FeeTranche`** — one instalment line in a class's échéancier.
- `belongs_to :class_group` (`allow_nil? false`); `label :string` (`allow_nil? false`,
  e.g. "Scolarité T1"), `amount :integer` (`allow_nil? false`, ≥ 0, FCFA),
  `due_date :date` (`allow_nil? false`), `position :integer` (`allow_nil? false`,
  ordering), denormalized `workspace_id :uuid` (`allow_nil? false`).
- `references` `on_delete: :delete` for `class_group`.

**`Payment`** — one recorded payment by a student.
- `belongs_to :enrollment` (`allow_nil? false`); `amount :integer` (`allow_nil? false`,
  > 0, FCFA), `paid_on :date` (`allow_nil? false`), `method` `PaymentMethod`
  (`allow_nil? false`), `reference :string` (nullable — e.g. a mobile-money txn id),
  `note :string` (nullable), `recorded_by_user_id :uuid`, denormalized
  `workspace_id :uuid` (`allow_nil? false`).
- `references` `on_delete: :delete` for `enrollment`.

**`FeeAdjustment`** — an optional per-student credit reducing what is owed.
- `belongs_to :enrollment` (`allow_nil? false`); `amount :integer` (`allow_nil? false`,
  ≥ 0, FCFA — a credit), `reason :string` (`allow_nil? false`, e.g. "Bourse", "APEE
  exonérée"), `recorded_by_user_id :uuid`, denormalized `workspace_id :uuid`
  (`allow_nil? false`).
- Identity `unique_adjustment [:enrollment_id]` (at most one adjustment per student;
  re-setting upserts). An upsert-capable create action identified by that identity.
- `references` `on_delete: :delete` for `enrollment`.

All three registered in the `TeacherAssistant.Academics` domain. `workspace_id` is set
from the class group / enrollment on create so fee reads stay single scoped queries.

## 2. Pure fee math — `Academics.FeeBalance`

A DB-free module (mirroring `Bulletins` / `Conduct`), operating on plain structs/maps:
- `compute(tranches, payments, adjustment_amount, on_date)` →
  `%{total_due, total_paid, balance, due_to_date, status}`:
  - `total_due` = sum of tranche amounts − `adjustment_amount` (floored at 0).
  - `total_paid` = sum of payment amounts.
  - `balance` = `total_due − total_paid` (may be negative on overpayment).
  - `due_to_date` = sum of tranche amounts with `due_date ≤ on_date`, minus the
    adjustment (floored at 0, capped at `total_due`).
  - `status`: `:paid_up` when `balance ≤ 0`; else `:on_track` when
    `total_paid ≥ due_to_date`; else `:behind` (owing `due_to_date − total_paid`).
- All integer arithmetic; no per-tranche allocation — a single running paid total is
  compared to the cumulative amount due by `on_date`. The "behind" shortfall is
  `due_to_date − total_paid`.

## 3. Context — `Academics.Fees`

New module (all Ash calls `authorize?: false`, tagged tuples, workspace-scoped, never
leak raw Ash errors):
- `list_tranches(class_group)` → `[%FeeTranche{}]` ordered by `position`.
- `add_tranche(class_group, attrs)` / `update_tranche(tranche, attrs)` /
  `delete_tranche(tranche)` — schedule editing; validate `amount ≥ 0`; set
  `workspace_id` from the class group; append `position` at the end on add.
- `record_payment(enrollment, attrs, recorded_by_user_id)` → `{:ok, %Payment{}} |
  {:error, term}`: validate `amount > 0` and `method` ∈ the enum (whitelist), set
  `workspace_id` from the enrollment's class group; sanitize Ash failure to a tagged
  atom.
- `delete_payment(payment)` → `:ok | {:error, term}`; `list_payments(enrollment)` →
  `[%Payment{}]` newest first.
- `set_adjustment(enrollment, attrs, recorded_by_user_id)` → upsert on
  `:unique_adjustment` (validate `amount ≥ 0`); `clear_adjustment(enrollment)` →
  deletes it.
- `student_balance(enrollment, on_date \\ Date.utc_today())` →
  `%{total_due, total_paid, balance, due_to_date, status}` via `FeeBalance.compute/4`
  (tranches from the enrollment's class group, that student's payments + adjustment).
- `class_balances(class_group, on_date \\ Date.utc_today())` →
  `%{enrollment_id => balance_map}` for the whole roster, computed from ONE scoped read
  of the class's tranches + all its enrollments' payments + adjustments (no N+1 per
  student). Every roster enrollment appears (zero payments → the schedule's due/status).

## 4. Access

New `Permissions.fees_manager?/1` = `admin?/1 or bursar?/1`. A fees manager sets
schedules and records payments/adjustments for any class in the workspace. The class
**form master** (`admin_or_form_master?/2`, true but not fees_manager) gets a
**read-only** balances/status view for their class. Everyone else is redirected to
`/school` with a flash. Every surface resolves the class via `fetch_owned_class_group/2`,
gates the mount, and re-checks `fees_manager?` in each mutating handler; the
enrollment/tranche/payment targets come from socket-loaded collections (never raw
client ids); the amount is parsed/bounded and the `method` whitelisted (no
`String.to_atom` on raw input); dates via `Date.from_iso8601/1`.

## 5. UI

Per-class fees page `/school/classes/:id/fees` (route in the `:school_workspace` live
session), linked from the class-detail page (fees-manager or form-master):
- **Fee schedule editor** — the class's tranches (label · amount FCFA · due date),
  with add / edit / delete for a fees manager; read-only rows for the form master. A
  running total of the schedule.
- **Payments & balances** — the class roster with, per student: total due · total paid
  · balance · a **status chip** (Soldé / À jour / En retard (−X FCFA)). A fees manager
  gets a **record-payment** action per student (amount, date defaulting today, method,
  optional reference + note) and can view/delete that student's payment history, plus
  set/clear the per-student adjustment (amount + reason). The form master sees the
  table and chips read-only (no record/adjust controls; forged events rejected).
- A compact "solde" indicator may also sit on the class-detail header for
  fees-manager / form-master.
- All amounts rendered as integer FCFA with a thousands separator via a small shared
  formatting helper.

## 6. Testing

- **Pure math (`FeeBalance`):** `due_to_date` sums only tranches due on/before the
  reference date; the three statuses (`:paid_up`, `:on_track`, `:behind`) at boundary
  cases; an adjustment reduces `total_due` and `due_to_date`; overpayment yields a
  negative balance and `:paid_up`; a future-dated tranche is excluded from
  `due_to_date`.
- **Context (`Fees`):** tranche add/update/delete with `position` append and
  `workspace_id` scoping; `record_payment` validates amount > 0 and method (invalid
  rejected, tagged error on write failure); `list_payments` newest first;
  `set_adjustment` upserts (one row, re-set replaces); `student_balance` composes math
  correctly; `class_balances` returns every roster enrollment in one scoped read (an
  entry-less student shows full due / behind), no N+1.
- **LiveView (fees page):** a fees manager adds a tranche, records a payment (balance +
  status update), sets an adjustment; a form master sees the page read-only (no
  controls) and a forged add-tranche / record-payment / set-adjustment event is
  rejected (no DB change); a non-member / cross-school class redirects; amounts are
  parsed defensively and a non-numeric / negative amount is rejected without persisting.
- **i18n / gate:** gettext extract + non-empty FR/EN msgstrs for every new msgid
  (payment methods, "Frais", "Tranche", "Échéance", "Montant", "Solde", "Payé", "Reste
  à payer", "À jour", "En retard", "Soldé", "Enregistrer un paiement", "Bourse /
  ajustement", "Motif", "Référence", access/flash strings, "FCFA"); `mix precommit`
  (full suite) green. Note: the precommit alias flag is misspelled
  `--warning-as-errors` (a no-op), so warnings do not gate — confirm the suite passes;
  the `format` step rewrites files in place, so commit any format-only diffs. A known
  `user_fixture` email-collision flake on `users_unique_email_index` can trip an async
  full run — re-run to confirm if only that fails.

## Notes / risks

- **Integer FCFA everywhere** — no Decimal, no minor unit. Validate amounts as
  non-negative (payments strictly positive) at the context layer; parse UI input
  defensively (reject non-integer / negative before any write).
- The status computation is display-only and must never gate a surface in this
  increment; `class_balances` feeds the bursar overview and the form-master view only.
- `class_balances` must batch: one read of the class's tranches, one of its
  enrollments' payments, one of the adjustments — then compute per student in memory,
  mirroring the batching fix pattern used in P2.9's `class_discipline/2`.
- Denormalize `workspace_id` onto all three resources; set from the class group /
  enrollment on create.
- `FeeAdjustment` is a single per-student credit (identity on `enrollment_id`) — enough
  for a bourse or APEE waiver; multiple stacked adjustments are YAGNI for v1.
- `on_delete: :delete` on the enrollment FKs means removing a student's enrollment
  cleans up their payments and adjustment; removing a class group cleans up its
  tranches (same cascade posture as attendance/discipline).
