# P2.10 — School fees, tranches & payment status Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the bursar a per-class fee échéancier (tranches), student payment recording, per-student adjustments, and a display-only balance + payment-status (à jour / en retard / soldé) — with no automatic gating.

**Architecture:** One enum + three Ash resources (`FeeTranche` per class-group, `Payment` + `FeeAdjustment` per enrollment). A pure `Academics.FeeBalance` module computes balance/status from tranches + payments + adjustment against a reference date. A new `Academics.Fees` context wraps CRUD + batched `class_balances`. A per-class fees LiveView (schedule editor + payments/balances table) reuses the P2.5/P2.9 access patterns; a new `Permissions.fees_manager?/1` gates it.

**Tech Stack:** Elixir, Ash 3, AshPostgres, Phoenix LiveView, gettext (FR default + EN).

## Global Constraints

- Ash 3 house style on every resource: `use Ash.Resource, otp_app: :teacher_assistant, domain: TeacherAssistant.Academics, data_layer: AshPostgres.DataLayer, authorizers: [Ash.Policy.Authorizer]`; `policy always() do authorize_if always() end`; `uuid_v7_primary_key :id`; `timestamps()`; FK `on_delete` inside `postgres do ... references do ... end end`.
- Enums are `Ash.Type.Enum` modules — never bare `:atom`.
- **All money amounts are integer FCFA** — no Decimal, no minor unit. Payments strictly `> 0`; tranche/adjustment amounts `≥ 0`. Validate at the context layer; parse UI input defensively (reject non-integer / negative before any write).
- Context functions call Ash with `authorize?: false`, return tagged tuples, never leak raw Ash errors.
- Double-gating on the fees LiveView: a UI `:if` gate AND a server-side re-check in each mutating handler. Class via `Academics.fetch_owned_class_group/2`. Targets (enrollments, tranches, payments) from socket-loaded collections, never raw client ids. Payment `method` via whitelist (no `String.to_atom`/`String.to_existing_atom` on raw input). Dates via `Date.from_iso8601/1`.
- **Display-only:** the payment status must NOT gate/block any surface in this increment.
- Access: `Permissions.fees_manager?/1` = `admin?/1 or bursar?/1` mutates; the class form master (`admin_or_form_master?/2`, not fees_manager) is read-only; everyone else redirected. No other new permission helpers.
- Migrations via `mix ash.codegen <name>` then `mix ecto.migrate`; commit the generated migration and `priv/resource_snapshots/` changes.
- Every new user-facing string is a gettext msgid with non-empty FR and EN msgstrs. `mix precommit` (full suite) must be green; its `format` step rewrites files in place — commit format-only diffs. (The precommit alias flag `--warning-as-errors` is misspelled and a no-op, so warnings do not gate; confirm the suite passes regardless. A known `user_fixture` email-collision flake on `users_unique_email_index` can trip an async full run — re-run to confirm if only that fails.)

### Task 4: Pure fee math — `Academics.FeeBalance`

**Files:**
- Create: `lib/teacher_assistant/academics/fee_balance.ex` (pure module, mirror the DB-free style of `lib/teacher_assistant/academics/conduct.ex`)
- Test: `test/teacher_assistant/academics/fee_balance_test.exs`

**Interfaces:**
- Consumes: `FeeTranche` structs (with `amount`, `due_date`), `Payment` structs (with `amount`), an integer `adjustment_amount`, a `Date`.
- Produces: `TeacherAssistant.Academics.FeeBalance.compute(tranches, payments, adjustment_amount, on_date)` → `%{total_due, total_paid, balance, due_to_date, status}`:
  - `total_due` = sum of tranche `amount` − `adjustment_amount`, floored at 0.
  - `total_paid` = sum of payment `amount`.
  - `balance` = `total_due − total_paid` (may be negative).
  - `due_to_date` = sum of tranche `amount` where `due_date ≤ on_date`, minus `adjustment_amount` (floored at 0, capped at `total_due`).
  - `status`: `:paid_up` when `balance ≤ 0`; else `:on_track` when `total_paid ≥ due_to_date`; else `:behind`.
  - All integer arithmetic; `adjustment_amount` defaults to 0 when there is no adjustment.

- [ ] **Step 1: Write the failing test.** Cover, with inline `%FeeTranche{}`/`%Payment{}` structs (no DB): `due_to_date` sums only tranches with `due_date ≤ on_date` and excludes a future-dated tranche; `:on_track` when paid exactly equals `due_to_date`; `:behind` when paid is one FCFA under `due_to_date`; `:paid_up` when `total_paid ≥ total_due` (incl. overpayment → negative balance); an `adjustment_amount` reduces both `total_due` and `due_to_date` and floors at 0; empty tranches/payments → zeros and `:paid_up`.

- [ ] **Step 2: Run — verify it fails.** `mix test test/teacher_assistant/academics/fee_balance_test.exs`. Expected: FAIL.

- [ ] **Step 3: Implement `compute/4`** (integer sums, `Date.compare/2` for the cutoff), DB-free like `conduct.ex`.

- [ ] **Step 4: Run — verify it passes.** Expected: PASS.
